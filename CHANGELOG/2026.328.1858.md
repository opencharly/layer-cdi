# 2026.328.1858 — docs(cdi): add the measured uid mapping and the HOME consequence to the two legal shapes

## Summary

The "host bind the workload must write" shape said container root IS the invoking host user but not what that means for any other uid or for HOME. Measured: --user 0 writes as host uid 1000, --user 1000 writes as 100999 and cannot write a user-owned directory, keep-id with a CDI device is crun EPERM (exit 126). Container root's HOME is /root while volumes mount under the image home, so a deploy in this shape must set HOME; measured without it python/node/huggingface_hub resolve under /root.

The keep-id-with-a-CDI-device failure named in the Summary is measured and root-caused:

```
$ podman run --rm --userns=keep-id:uid=1000,gid=1000 --device nvidia.com/gpu=all --entrypoint /bin/sh ghcr.io/opencharly/immich-cdi:2026.328.1448 -c 'true'
crun: mount_setattr `/usr/bin/nvidia-cuda-mps-control`: Operation not permitted
```

Root cause: `--userns=keep-id` creates a user namespace in which crun cannot apply the CDI spec's
~62 FILE mounts (`mount_setattr` is refused for a subuid-owned path); the documented occurrence is
opencharly/plugin-deploy-pod#81 (exit 126). It is the reason the CDI + host-owned-volume branch
cannot use keep-id and runs container root under `userns=host`.

The alternatives to `-allow_other` were spiked on the same vault: gocryptfs 2.7 rejects
`-o allow_root` (`unknown flag: --allow_root`) and offers no `force_owner`; a plain directory at
`0755` does not admit a non-owner without `-allow_other`; and the one shape that needs no
`-allow_other` is the owner one — container root under `userns=host`.
