# 2026.323.0302 — chore(pins): require layer-cuda v2026.323.0252 so a CDI pod composes no driver layer

## Summary

One line, and it closes the last hole in a nine-repo cutover: this candy's `require:` for the CUDA
toolkit moves from `layer-cuda:v2026.323.0138` to **`v2026.323.0252`**.

Diff, from `git diff --stat origin/main...HEAD` — one file:

```
 charly.yml | 10 +++++++++-
 1 file changed, 9 insertions(+), 1 deletion(-)
```

**Why the pin, and not something else.** `v2026.323.0138` carries `require:
layer-nvidia:v2026.320.1938`. A `require:` is **target-blind** — it is ordering metadata, and it
travels to every image that composes the layer. So every **pod** that composed `layer-cdi` also
composed the **VM driver user-space**, and `layer-nvidia`'s `nvidia-ctk` plan assertions then ran on
an image whose composition deletes that binary:

```
FAIL  check the nvidia-ctk CLI binary lands on /usr/bin   [layer-nvidia:4]  exists=false
FAIL  check nvidia-ctk runs and reports a version number  [layer-nvidia:5]  exit=127
```

That is measured on `opencharly/distro-cachyos`'s `check-comfyui-pod` bed (head `ed7f0545` of
distro-cachyos#206), and it is the only reason that bed has never gone green.

`v2026.323.0252` (opencharly/layer-cuda#30) keeps the **same anchored `drv=` predicate** the
assertion below twins (`libcuda.so*` + an explicit `libcudadebugger.so*`) and **drops `require:
layer-nvidia`** — the toolkit no longer drags the driver. So this is a pure `require:` move: the
`drv=` twin between `cdi-no-baked-driver-libs` and `cuda-drop-driver-userspace` is byte-identical
across the bump, which is why the pin and the assertion still name the same release.

**What the consumer can now do, and could not before.** Within one box scope the resolver rejects
two different tags for the same candy, so a pod could not name `layer-cuda:v2026.323.0252` beside
this layer while this layer required `v2026.323.0138`:

```console
$ charly box validate
Notice: candy github.com/opencharly/layer-cuda resolved to multiple git tags with differing
  content within one scope (box=nvidia-cdi); using newest referenced v2026.323.0252 …
charly: error: command "validate": validation error: candy
  github.com/opencharly/layer-cuda resolved to multiple git tags with differing content within
  one scope (box=nvidia-cdi); …
```

After this release, a consumer names `layer-cdi` at the new tag and `layer-cuda:v2026.323.0252` —
one tag, one scope, and a composed pod image with no driver layer. The consumer leg
(`opencharly/distro-cachyos`, successor to #206) is pinned to it.

## Change classification

One pin value in one candy. Consumers that compose `layer-cdi` (every CDI GPU pod, via `pod-cdi`)
now resolve `layer-cuda:v2026.323.0252`, whose `require:` no longer names `layer-nvidia`. Their
images therefore stop composing the VM driver user-space — which is the contract they were always
supposed to have, and which several of them currently violate without knowing it.

**Breaking change + rollback:** nothing breaks in this repo, and the break is the intended one
downstream — a *pod* built on this layer loses a baked driver layer it must never have carried, so
any consumer relying on an image-baked driver in a CDI pod breaks by design (none should; a
passthrough guest is served by `opencharly/vm-nvidia`, which composes `layer-nvidia` itself). A VM
image composes `layer-nvidia` + `layer-cuda` directly and does not compose this layer, so it is
unaffected. Rollback is the reverse of this diff: restore the single `require:` line to
`layer-cuda:v2026.323.0138`, which reinstates the driver dependency in every CDI pod.
