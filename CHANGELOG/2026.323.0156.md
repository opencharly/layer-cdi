# 2026.323.0156 — fix(cdi): stop counting the CUDA runtime as a baked driver library

## Summary

`cdi-no-baked-driver-libs` decided "no driver library is baked" with the **prefix** glob `libcuda*.so*`
— the same over-broad pattern `opencharly/layer-cuda#23` fixed in the strip. The `libcuda` prefix
family is four libraries, and only two of them are the driver:

| family | libraries | must be in the image? |
|---|---|---|
| DRIVER | `libcuda.so{,.1,.<ver>}` | no — injected by the CDI spec |
| DRIVER | `libcudadebugger.so{,.1,.<ver>}` | no — injected by the CDI spec |
| RUNTIME | `libcudart.so{,.13,.13.5.37}`, `libcudart_static.a`, `libcudadevrt.a` | **yes** |
| COMPUTE | `libcublas*`, `libcudnn*`, `libnvrtc*`, `libcurand*`, `libcufft*`, … | **yes** |

Against the layout `layer-cuda`'s anchored strip now leaves behind, the assertion counted the last two
families as violations and turned every pod image build red:

```
$ CDI_LIB_DIRS=<post-fix layout> sh <the cdi-no-baked-driver-libs step, origin/main>
cdi: driver libraries still baked: 3
exit=1
```

The three are `libcudart.so`, `libcudart.so.13`, `libcudart.so.13.5.37` — the CUDA runtime
`layer-cuda` installs and stitches, which must be there.

**The fix is not a new definition.** `opencharly/layer-cuda`'s `cuda-drop-driver-userspace` holds the
ONE definition of "driver user-space" in its `drv=` variable; `cdi-no-baked-driver-libs` now carries the
**same assignment, byte for byte**, so a `diff` of the two blocks is the drift control:

```
$ diff <drv= block, layer-cuda v2026.323.0138> <drv= block, this branch>; echo $?
0
$ cat <this branch's drv=>                       # the twin, unchanged quotes and all
                drv="-name libnvidia-*.so* -o -name libcuda.so* -o -name libcudadebugger.so* \
                -o -name libnvcuvid.so* -o -name libnvoptix.so* -o -name libGLX_nvidia.so* \
                -o -name libEGL_nvidia.so* -o -name libGLESv1_CM_nvidia.so* \
                -o -name libGLESv2_nvidia.so*"
                vdpau="-name libvdpau_nvidia.so*"   # outside the twin, see below
```

`libcudadebugger.so*` is listed **explicitly**: it is driver user-space but does not carry the
`libcuda.so` stem, so anchoring alone would leave it behind.

`libvdpau_nvidia.so*` is the one driver library the producer covers by a **tree** (`rm -rf
/usr/lib/vdpau`) rather than by a top-level pattern, so it stays as its own member beside the twin and
is also counted by the tree loop. Measured, so the shape is justified rather than assumed:

```
$ ls -ld /usr/lib64 ; stat -c '%d:%i %n' /usr/lib/vdpau /usr/lib64/vdpau
lrwxrwxrwx ... /usr/lib64 -> lib
32:143773 /usr/lib/vdpau
32:143773 /usr/lib64/vdpau            <- same directory: /usr/lib64/vdpau IS /usr/lib/vdpau
$ ls -1 /usr/lib/vdpau/
libvdpau_nvidia.so  libvdpau_nvidia.so.1  libvdpau_nvidia.so.615.78.08  libvdpau_trace.so ...
```

and the top-level name cannot false-red: `/usr/lib{,64}/libvdpau.so*` is **Mesa's** shim, a different
name (measured in `nvidia-cdi:check-comfyui-pod-2026.323.0032`).

**They cannot be shared, and this PR says so at both ends.** Each is a shell fragment inside a
different repo's `charly.yml` plan step, and neither repo has an `include` that reaches into the
other's plan. So the duplication is deliberate and NAMED: the step's comment names
`opencharly/layer-cuda` and the tag `v2026.323.0138` it must track, `.agents/skills/cdi-layer` carries
the byte-for-byte rule, and the reciprocal reference on the producer's side is filed as
`opencharly/layer-cuda#27`.

`require:` moves `layer-cuda` `v2026.321.1520` → **`v2026.323.0138`** (`origin/main`, commit `1514520`).
Pin and assertion move together. **The version boundary is `v2026.323.0124`**: that is the release that
landed the anchored strip (`layer-cuda#24`), and every release before it strips with the prefix glob and
deletes the runtime. `v2026.323.0138` (`#26`) carries the *same* `drv=` — verified, the two tags' blocks
`diff` empty — and only extends the producer's survival assertion to the toolkit's static archives; it
is pinned because it is the newest of that line.

### 2. The assertion executed against fixtures — failing without, passing with, three mutation arms

Fixtures use **real filenames**: the host's `/usr/lib` driver names (module `615.78.08`, measured with

Each run extracts the step's `command:` from `charly.yml` verbatim and executes it with the overridable
directories. `clean` = post-fix layout (runtime + compute present, no driver); `driver` = clean + the
host's driver libraries; `debugger` = clean + `libcudadebugger.so.615.78.08` alone; `vdpau-top` /
`vdpau-tree` = clean + `libvdpau_nvidia.so.615.78.08` at top level / inside a `vdpau/` tree;
`mesa` = clean + a top-level `libvdpau.so.1` (Mesa's legitimate shim).

```
BEFORE (origin/main)      clean 3 exit=1   driver 18 exit=1   debugger 4 exit=1
                          vdpau-top 4 exit=1  vdpau-tree 4 exit=1  mesa 3 exit=1

AFTER  (this branch)      clean 0 exit=0   driver 15 exit=1   debugger 1 exit=1
                          vdpau-top 1 exit=1  vdpau-tree 1 exit=1  mesa 0 exit=0
```

The two vdpau arms are green-then-red in the right direction (`0` on a correct layout, `1` when the
driver library is present in either shape), and `mesa` proves the restored member does not red the
legitimate neighbour.

## Change classification

- **Kind:** layer (candy manifest) — one `run:` step's predicate, one `require:` tag, and the
  claim-keyed prose sweep of the same predicate in `AGENTS.md` and both skills.
- **Blast radius:** every image that composes `cdi` and `layer-cuda` — `pod-cdi` and the pod images
  built on it. Any such build whose `layer-cuda` resolves to **`≥ v2026.323.0124`** is red before this
  change; after it they are correct, because the assertion and the strip now agree on one definition.
- **Rollback:** revert the commits. Builds go back to reporting `cdi: driver libraries still baked: 3`
  on a correct layout, i.e. the block this PR removes.
- **Breaking change + rollback:** not a cutover (no `!`): nothing that previously built correctly stops
  building, and a consumer that keeps its own `layer-cuda` pin is unaffected until it moves. The one
  behavioural change is that the assertion no longer fires on the CUDA runtime — which is the defect.

## Filed issues

- `opencharly/layer-cuda#27` — the reciprocal cross-reference in the strip's `drv=` comment: name
  `layer-cdi`'s copy, the byte-for-byte rule and the `require:` tag. Comment-only, in a different repo

- `opencharly/layer-cuda#28` — the strip's `rm -rf` names `/usr/lib/vdpau` only, so a distro whose

  nowhere here on purpose: tripping it in the consumer would red a build the producer cannot make
  correct, which is the false-red class this PR removes.
- `opencharly/layer-cdi` — the `.agents/skills/cdi-layer/SKILL.md` table named a `cdi-drop-baked-driver`
  step that has not existed since the strip moved to `layer-cuda`, and called the assertions `check:`
