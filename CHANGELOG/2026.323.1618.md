# 2026.323.1618 — fix(cdi)!: derive the driver assertion's layouts from the producer's one list

## Summary

`opencharly/layer-cuda#28` landed as `v2026.323.1604` (squash `5f5bb77070fa4a25ec4780259c870ed841794d65`): `cuda-drop-driver-userspace` now walks `/usr/lib{,32,64}` for the driver libraries and derives its `nvidia`/`vdpau` tree removals and its xorg removal from that SAME `libs=` list. This repo had not moved with it — `cdi-no-baked-driver-libs` still `require:`d `v2026.323.0252` and counted one hard-coded `/usr/lib` tree set.

Two defects, one cutover:

1. **The pin was stale.** `require: layer-cuda` moves `v2026.323.0252` → `v2026.323.1604`. Until it moves, NO composing box can adopt the fixed producer: bumping only the box's `layer-cuda` pin makes `layer-cdi`'s own `require:` the SECOND tag in the same box scope, and `charly box validate` refuses (opencharly/layer-cdi#12, measured below).
2. **The assertion described a different set from the one the producer strips.** It named `/usr/lib/nvidia`, `/usr/lib64/nvidia` and `/usr/lib/vdpau` and ONE xorg path, so `/usr/lib32/vdpau`, `/usr/lib32/nvidia`, `/usr/lib64/vdpau` and the `/usr/lib32`/`/usr/lib64` xorg drivers were invisible to it. The assertion now derives its three surfaces — the top-level libraries, the `nvidia`/`vdpau` trees, and the xorg driver — from ONE layout list (`layouts=${CDI_LIB_DIRS:-/usr/lib /usr/lib32 /usr/lib64}`), exactly as the producer derives its own, so the two halves describe ONE set.

The `drv=` pattern block is deliberately untouched: it is the byte-identical twin of the producer's, and `diff` of the two blocks remains the drift control (pasted below).

## Change classification

**Breaking change + rollback:** breaking for CONSUMERS, not for this repo. A project that composes `layer-cdi` keeps working only when its `layer-cuda` pin moves to `v2026.323.1604` in the same edit as its `layer-cdi` pin — any other `layer-cuda` tag in the same box scope makes `charly box validate` refuse with the same-scope tag skew quoted above.
